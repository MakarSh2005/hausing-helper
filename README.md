## 1. Назначение решения

Жилец сталкивается с поломкой — течёт батарея, не работает лифт, не вывозят мусор — и не знает, куда звонить, в какой срок обязаны устранить и что делать, если не устранили. Номер УК ищут в квитанции, обращение по телефону не оставляет следа, а нормативные сроки знают единицы.

«Жилищный помощник» закрывает этот путь целиком внутри MAX:

- **определяет дом и управляющую компанию** по адресу — из справочника домов (3 973 дома во всех семи районах Казани, 19 управляющих компаний; данные ГИС ЖКХ и ЕГРЮЛ);
- **принимает заявку** с описанием и фото, сам определяет категорию и ответственного — УК или регионального оператора по вывозу мусора;
- **называет нормативный срок** со ссылкой на пункт норматива (Правила № 354, № 416, № 170) и ведёт живой таймер;
- **напоминает**, когда срок истёк, и **готовит текст жалобы** в Госжилинспекцию Республики Татарстан;
- показывает контакты УК и аварийных служб, статусы заявок, «Соседи уже сообщили» (сколько заявок какой категории подали соседи по дому), принимает оценку работы УК, отвечает на типовые вопросы.

Сервис работает в тестовом режиме: заявки хранятся в сервисе и **в УК автоматически не передаются** — об этом честно сказано в боте и приложении (см. [раздел 14](#14-известные-ограничения)).

## 2. Основной пользовательский сценарий

```
Бот:  «Начать» → адрес («Ибрагимова 12») → бот находит дом в справочнике → «Да, это мой дом»
      → номер квартиры → подъезд → «Готово!» + две кнопки: «Приложение с заявками», «Сменить адрес»

Мини-приложение:
      «Подать заявку» → описание («Не работает лифт») → категория определяется сама, видно
      «Кому» и «Срок по нормативу» → фото (до 5, необязательно) → «Отправить заявку»
      → карточка REQ-2026-NNNNN: ответственный, срок, живой таймер, хронология

Дальше: статус меняется (в демо-режиме — по времени) → истёк срок — бот пишет в чат
      с кнопкой «Открыть заявку» → «Проблема решена» и оценка УК
                                   или «Не решена — жалоба в Госжилинспекцию» (готовый текст)
```

Бот — входная дверь: адрес и квартира привязываются один раз, дальше у жильца ровно две кнопки. Всё остальное — в мини-приложении. Бот пишет сам только в двух случаях: на «запах газа» — сразу памятка с 104 и 112, и когда истёк срок по заявке.

## 3. Состав и архитектура решения

```
          Жилец в MAX (телефон, веб)
           │                    │
   чат с ботом          мини-приложение (WebView MAX)
           │                    │  MAX Bridge: подписанные initData
           ▼                    ▼
   MAX Bot API  ──webhook──►  ┌──────────────── один контейнер (Node.js 20) ────────────────┐
  (platform-api2.max.ru) ◄──  │  Express                                                    │
           сообщения, кнопки  │  ├─ POST /webhook   → разбор событий → сценарии бота (FSM)   │
                              │  ├─ /api/*          → API мини-приложения (сессия JWT)       │
                              │  ├─ /app/*          → собранное мини-приложение (React)      │
                              │  ├─ /health, /bot   → проверка живости, имя бота             │
                              │  └─ таймер 60 с     → напоминания о просроченных заявках     │
                              │  Prisma → SQLite /data/app.db,  фото → /data/photos          │
                              └─────────────────────────────────────────────────────────────┘
```

**Компоненты.** Один Docker-образ и один процесс: бэкенд раздаёт и API, и собранное мини-приложение с того же адреса, поэтому CORS не нужен. Состояние — только в SQLite на постоянном томе `/data`, в памяти процесса ничего важного нет: рестарт не теряет ни заявок, ни шага онбординга.

| Часть | Технологии | Где |
|---|---|---|
| Бот | Node.js 20, TypeScript, Express 5, Zod | `backend/src/bot`, `backend/src/webhook`, `backend/src/max` |
| API мини-приложения | Express, собственный HS256 JWT (1 ч), проверка подписи MAX | `backend/src/api`, `backend/src/auth` |
| Предметная логика | нормативы, категории, жалоба, хронология, поддержка | `backend/src/domain`, `backend/src/requests`, `backend/src/support` |
| Данные | Prisma 6 + SQLite, 6 миграций, seed справочника | `backend/prisma` |
| Мини-приложение | React 19, Vite, MAX UI | `webapp` |
| Справочник домов | JSON из Excel-шаблона (скрипт на Python) | `backend/prisma/reference`, `tools/import_houses.py` |
| Сборка и запуск | многоэтапный Dockerfile, compose, entrypoint | `Dockerfile`, `compose.yaml`, `deploy/` |

```
housing-helper/
├── Dockerfile · compose.yaml · amvera.yml · .env.example
├── deploy/                 entrypoint.sh (миграции → seed → бот), netcheck.mjs (сеть до MAX)
├── tools/import_houses.py  Excel → kazan-houses.json
├── backend/
│   ├── certs/              сертификаты УЦ Минцифры (TLS к MAX API)
│   ├── prisma/             schema.prisma, migrations/, seed.ts, reference/kazan-houses.json
│   ├── src/
│   │   ├── index.ts        запуск, проверка токена, подписка на вебхук, напоминания
│   │   ├── config.ts       единственное место, где читается окружение (Zod)
│   │   ├── max/            клиент MAX API: ретраи, 429, таймауты, TLS; клавиатуры; polling
│   │   ├── webhook/        секрет → 200 → разбор → идемпотентность → лимит → сценарий
│   │   ├── bot/            сценарии бота и доступ к БД
│   │   ├── api/            API мини-приложения
│   │   ├── auth/           проверка initData MAX, сессионные токены
│   │   ├── domain/         нормативы, категории, адреса, статусы, хронология, жалоба
│   │   ├── requests/       подача заявки (общая для бота и API)
│   │   ├── photos/         хранение фото заявок
│   │   └── support/        автоответы поддержки
│   └── test/               209 тестов (node:test)
└── webapp/src/             экраны мини-приложения
```

**Ключевые решения.**
- Вебхук отвечает `200` сразу, до обработки, и защищён от повторов (`processed_updates`): MAX ретраит медленные ответы, а двойная обработка создала бы дубли заявок.
- События одного пользователя обрабатываются строго по очереди — двойное нажатие не читает одно состояние дважды.
- Статус заявки в демо-режиме вычисляется из времени создания при чтении, а не таймерами в памяти — переживает рестарт.
- Напоминание: сначала отметка в базе, потом отправка — при сбое сети оно может потеряться, но не задвоится.
- Пользователь в API берётся только из проверенного токена; чужая заявка — `404`, а не `403`.
- Бот работает только в личном диалоге: сообщения из групповых чатов игнорирует и не записывает `chat_id` группы как диалог жильца.

## 4. Запуск одной командой через Docker

```bash
git clone <репозиторий> housing-helper && cd housing-helper
cp .env.example .env          # вписать MAX_BOT_TOKEN
docker compose up --build     # ← одна команда запускает все компоненты
```

Поднимается один контейнер `app` — тот же образ, что на стенде. При старте: миграции базы → загрузка справочника домов → проверка сети до MAX → бот и сервер.

Проверка:
- http://localhost:3000/health → `{"status":"ok"}`;
- http://localhost:3000/app/ — мини-приложение; вне MAX оно покажет «Откройте из чата с ботом» — так и должно быть, вход возможен только по подписанным данным MAX;
- в логе: `сервер запущен на порту 3000, режим polling` и `MAX: токен действителен`.

По умолчанию локально бот работает в режиме `MAX_MODE=polling`: сам забирает сообщения у MAX, поэтому домен и HTTPS не нужны. **Важно:** у рабочего бота стенда оформлена подписка на вебхук, а пока она есть, MAX не отдаёт события через polling. Локальный контейнер с тем же токеном запустится, но сообщений не получит (в логе будет предупреждение). Для локальной проверки нужен отдельный тестовый бот.

Время сборки: шаги без Docker с пустым кешем npm — 25 с; с загрузкой базовых образов и движков Prisma — ориентир 1–2 минуты.

## 5. Необходимые параметры окружения

| Что | Требование |
|---|---|
| Docker | Docker Engine 24+ с Compose v2 (`docker compose`), Linux / macOS / Windows (WSL2) |
| Ресурсы | 1 vCPU, 512 МБ ОЗУ для работы (на сборку — 1 ГБ), 1 ГБ диска под образ и том |
| Сеть | исходящий HTTPS до `platform-api2.max.ru:443`; при сборке — до Docker Hub и npm registry |
| Токен | токен бота MAX (`MAX_BOT_TOKEN`) |
| Для режима webhook | публичный HTTPS-адрес с сертификатом доверенного центра (самоподписанный MAX не принимает) и секрет `MAX_WEBHOOK_SECRET` |
| Мини-приложение внутри MAX | адрес `https://<домен>/app/` привязан к боту на платформе MAX для партнёров; без привязки бот даёт ссылку со входом, и приложение открывается в браузере |
| Без Docker | Node.js 20.6+ и npm (см. [приложение A](#a-запуск-без-docker)) |

TLS до MAX API: сертификат `platform-api2.max.ru` выпущен УЦ Минцифры, которому Node.js не доверяет по умолчанию. Корневые сертификаты лежат в `backend/certs` и подключаются только к запросам к MAX; проверка TLS не отключается.

## 6. Переменные окружения

Все переменные читаются в одном месте — `backend/src/config.ts` — и проверяются при старте: при ошибке сервис не запускается и называет переменную (значения секретов в сообщение не попадают). Пустая строка в `.env` значит «не задано». Шаблон — `.env.example`, реальные значения — только на служебном слайде презентации и в переменных хостинга.

| Переменная | Обязательна | По умолчанию | Назначение |
|---|---|---|---|
| `MAX_BOT_TOKEN` | **да** | — | токен бота MAX (секрет) |
| `MAX_MODE` | нет | `webhook` (в `.env.example` — `polling`) | `polling` — бот сам забирает события (локально); `webhook` — MAX присылает события на сервер |
| `MAX_WEBHOOK_SECRET` | в режиме `webhook` | — | секрет вебхука: 5–256 символов, латиница, цифры, дефис (секрет) |
| `PUBLIC_BASE_URL` | при `MAX_AUTO_SUBSCRIBE=true` | — | публичный `https://`-адрес сервера: на него подписывается вебхук, из него строятся ссылки на мини-приложение |
| `MAX_AUTO_SUBSCRIBE` | нет | `false` | `true` — оформить подписку на вебхук при старте (хостинг без консоли) |
| `MINIAPP_BUTTON` | нет | `open_app` | `open_app` — кнопка MAX запускает мини-приложение внутри MAX; `link` — ссылка со входом |
| `SESSION_JWT_SECRET` | нет | производится из токена бота | ключ подписи сессий мини-приложения, не короче 32 символов (секрет) |
| `SESSION_TTL_SECONDS` | нет | `3600` | срок жизни сессии мини-приложения |
| `DATABASE_URL` | **да** | в Docker `file:/data/app.db` | путь к SQLite; в Docker задаётся образом и `compose.yaml` |
| `DATA_DIR` | нет | `./data`, в Docker `/data` | папка для фото заявок |
| `PORT` | нет | `3000` | порт HTTP-сервера внутри контейнера |
| `NODE_ENV` | нет | `development`, в Docker `production` | режим логов |
| `LOG_LEVEL` | нет | `info` | `fatal` … `trace` |
| `LOG_RAW_UPDATES` | нет | `false` | писать сырые события MAX в лог — только для сверки формата (в них тексты пользователей) |
| `MOCK_AUTO_STATUS_CHANGE` | нет | `false` (в `.env.example` — `true`) | демо: статус «принята» через 30 с, «в работе» через 5 мин, с пометкой «демо» |
| `DEMO_DUE_MINUTES` | нет | — | демо: напоминание через N минут после подачи вместо нормативного срока; сам срок в заявке не меняется |
| `WEBHOOK_RATE_LIMIT_PER_MIN` | нет | `100` | лимит событий вебхука на одного пользователя в минуту |
| `MAX_API_URL` | нет | `https://platform-api2.max.ru` | адрес MAX Bot API |
| `MAX_CA_FILE` | нет | сертификаты из `backend/certs` | свой файл корневых сертификатов для TLS к MAX; `none` — не добавлять |
| `WEBAPP_DIR` | нет | `webapp` | папка собранного мини-приложения (в образе — `/app/webapp`) |
| `BACKEND_PORT` | нет | `3000` | порт на компьютере для `docker compose` |

На стенде Amvera заданы: `MAX_BOT_TOKEN`, `MAX_WEBHOOK_SECRET`, `PUBLIC_BASE_URL`, `MAX_AUTO_SUBSCRIBE=true`, демо-переменные; `MAX_MODE=webhook`, `DATA_DIR` и `DATABASE_URL` задаёт Dockerfile.

## 7. Используемые порты

| Порт | Где | Назначение |
|---|---|---|
| `3000/tcp` | внутри контейнера (`PORT`) | HTTP: `/webhook`, `/api/*`, `/app/*`, `/health`, `/bot` |
| `${BACKEND_PORT:-3000}` | на компьютере | проброс `docker compose` на порт 3000 контейнера |
| `443/tcp` исходящий | из контейнера | MAX Bot API `platform-api2.max.ru` |

HTTPS на стенде обеспечивает хостинг (Amvera принимает 443 и проксирует на порт 3000 контейнера — `containerPort: 3000` в `amvera.yml`). Других портов и сервисов (отдельной базы, очередей, кешей) нет.

## 9. Внешние сервисы и интеграции

| Сервис | Как используется | Статус |
|---|---|---|
| **MAX Bot API** `platform-api2.max.ru` | `GET /me` (проверка токена), `POST /messages`, `POST /answers` (ответ на кнопки), `POST/GET/DELETE /subscriptions` (вебхук), `GET /updates` (polling). Кнопки `callback`, `link`, `open_app`. Таймаут 5 с, ретраи с паузой, учёт 429 | реальная интеграция |
| **Вебхук MAX → сервер** | `POST /webhook` с заголовком `X-Max-Bot-Api-Secret`; события `message_created`, `bot_started`, `message_callback` | реальная интеграция |
| **Мини-приложения MAX** | запуск кнопкой `open_app`; вход по подписанным `initData` (HMAC-SHA256 по алгоритму из документации MAX, проверен эталонным примером); MAX Bridge: кнопка «Назад», открытие ссылок MAX | реальная интеграция; адрес приложения привязан к боту организаторами хакатона |
| **Диплинки** | `https://max.ru/t186_hakaton_max_bot?start=<код дома>` — сразу предлагает нужный дом (для QR-кода в подъезде) | реальная интеграция |
| **ГИС ЖКХ (через mingkh.ru), ЕГРЮЛ, сайты УК** | источник справочника домов и УК; выгрузка на 29.09.2026, названия УК сверены с ЕГРЮЛ, телефоны — с сайтами УК 30.09.2026; в сервисе — файлом | не онлайн-интеграция, данные реальные |
| **Нормативные акты** | ПП РФ № 354, ПП РФ № 416, Правила Госстроя № 170 — сроки и основания в `backend/src/domain/norms.ts` | реальные нормы, сверены 24.09.2026 |
| **Госжилинспекция РТ, Госуслуги** | жалоба формируется текстом, жилец отправляет её сам | без интеграции |
| **Управляющие компании** | заявки в УК **не передаются** (нет открытого API УК) | смоделировано: тестовый режим |
| **Региональный оператор ТКО, РСО, фонд капремонта** | организации в справочнике — демо, с пометкой «(демо)» в названии | смоделировано |
| **Amvera Cloud** | хостинг стенда: сборка по Dockerfile, HTTPS, постоянный том `/data` | инфраструктура |

## 10. Описание работы с данными

**Хранилище.** Одна база SQLite (`/data/app.db`) и папка фото (`/data/photos`) на постоянном томе. Схема — `backend/prisma/schema.prisma`, изменения — только миграциями (`backend/prisma/migrations`), они применяются автоматически при старте контейнера.

| Таблица | Что хранит |
|---|---|
| `users` | user_id MAX, chat_id диалога с ботом (для напоминаний), имя, ник и фото профиля MAX |
| `apartments` | привязка жильца: дом, номер квартиры, подъезд |
| `houses`, `organizations` | справочник домов и управляющих компаний (загружается seed) |
| `responsible_orgs` | категория → ответственная организация → нормативный срок (из `norms.ts`) |
| `requests` | заявки: номер, категория, описание, снимок адреса, статус, срок, отметка о напоминании, оценка |
| `request_attachments` | фото заявок (ссылка на файл на диске) |
| `request_counters` | счётчик номеров REQ-ГГГГ-NNNNN |
| `user_sessions` | шаг онбординга в боте (переживает рестарт) |
| `processed_updates` | ключи обработанных событий MAX — защита от дублей, чистятся через сутки |
| `tariffs`, `capital_repair_works` | заложены схемой, в текущей версии не используются |

**Персональные данные и безопасность.**
- Номер квартиры, описания заявок, токены и `initData` в журнал не пишутся; в журнале — user_id, номер заявки, категория, код дома. В поддержке пишется только тема вопроса, не его текст.
- Заявку, её фото и текст жалобы видит только автор: фильтр по пользователю — в самом запросе к базе. «Соседи уже сообщили» показывает только количество заявок по категории, без текста, квартир и имён.
- Фото принимаются до 5 на заявку и до 10 МБ; тип определяется по содержимому файла, а не по заголовку; отдаются только владельцу.
- Адрес в заявке — снимок на момент подачи: смена квартиры не меняет старые заявки и жалобы.
- Телефоны УК показываются только из проверенного справочника и при корректной контрольной цифре ИНН.
- Лимиты: 100 событий вебхука и 60 запросов API в минуту на пользователя, 30 входов в минуту на IP.
- Секретов в репозитории нет: `.env` в `.gitignore`, в `.env.example` — пустые значения.

**Что реальное, что смоделировано.** Реальные: справочник 3 973 домов и 19 УК (ГИС ЖКХ, ЕГРЮЛ), нормативные сроки и основания, вся логика заявок и сроков. Смоделированы: передача заявки в УК (не происходит), смена статуса «принята» / «в работе» (в демо-режиме по времени, с пометкой «демо»), организации ТКО, РСО, ГЖИ и фонда капремонта.

**Резервная копия** — копия файла `/data/app.db` и папки `/data/photos` (на стенде — средствами хостинга, локально — `docker compose cp app:/data ./backup`).

## 12. Пошаговый сценарий проверки

На стенде (или локально с тестовым ботом):

1. Откройте https://max.ru/t186_hakaton_max_bot → «Начать». Бот здоровается и просит адрес.
2. Напишите `Ибрагимова 12`. Бот: «Нашёл ваш дом в справочнике: пр-кт Ибрагимова, д. 12» и управляющую компанию → «Да, это мой дом».
3. Напишите номер квартиры, например `42`, выберите подъезд `2`. Бот: «Готово! Квартира привязана» и две кнопки.
4. Нажмите «Приложение с заявками». Откроется мини-приложение: «Жилищный помощник», вкладки «Квартира» и «Заявки».
5. «Квартира»: адрес, данные дома, УК с телефонами, кнопка «Сменить адрес». Иконка телефона вверху — аварийные номера (диспетчер УК, 104, 112).
6. «Заявки» → «Подать заявку». Опишите: `Не работает лифт, застряли между этажами`. Категория «Лифт» выберется сама; видно «Кому» и «Срок по нормативу: устранить неисправность лифта — не более 1 суток». При желании приложите фото → «Отправить заявку».
7. Откроется карточка `REQ-2026-NNNNN`: ответственный, адрес, живой таймер срока, хронология. Через 30 с статус станет «принята» с пометкой о демо-режиме, на колокольчике появится счётчик.
8. Через `DEMO_DUE_MINUTES` минут бот пришлёт в чат демо-напоминание («так бот напишет, когда истечёт нормативный срок») с кнопкой «Открыть заявку». Когда истекает настоящий нормативный срок, приходит напоминание «Срок по заявке … истёк», а в карточке появляется «Не решена — жалоба в Госжилинспекцию»: готовый текст с адресом, нормативом и сроком и кнопка «Скопировать». Быстрее всего это увидеть на заявке с коротким сроком — например, `засор в раковине` (2 часа).
9. Нажмите «Проблема решена» → поставьте оценку от 1 до 5. Средняя оценка появится у УК на вкладке «Квартира».
10. Кнопка «?» в углу — поддержка: спросите «Какие сроки у заявок?» или «Как связаться с УК?».
11. Проверка безопасности: напишите боту `пахнет газом` — сразу памятка с 104 и 112, заявка не оформляется.
12. Проверка устойчивости: перезапустите контейнер (`docker compose restart`) — привязка, заявки и срок на месте, бот продолжает с того же шага.

## 14. Известные ограничения

- **Заявки не передаются в УК.** У управляющих компаний нет открытого API; сервис фиксирует обращение, срок и готовит жалобу, а статусы «принята» / «в работе» в демо-режиме меняются по времени с пометкой «демо». Это сказано жильцу в боте и в карточке заявки.
- **Покрытие — 3 973 дома 19 управляющих компаний Казани.** Дома других УК, ТСЖ и ЖСК бот честно не находит. Справочник обновляется импортом Excel, онлайн-связи с ГИС ЖКХ нет.
- **Демо-организации.** Региональный оператор ТКО, РСО, ГЖИ и фонд капремонта — синтетические, с пометкой «(демо)».
- **Мини-приложение открывается внутри MAX** только по адресу, привязанному к боту на платформе MAX (привязку делают организаторы). В браузере — только по ссылке со входом от бота (код на сутки).
- **Уведомления жильцу** — только сообщением бота (мини-приложение не умеет присылать push); бот пишет сам лишь при истечении срока и на запах газа.
- **Один экземпляр.** SQLite и очередь событий в памяти рассчитаны на один контейнер; для нескольких экземпляров нужна PostgreSQL и общая блокировка напоминаний.
- **Polling и webhook на одном боте несовместимы**: пока у бота есть подписка на вебхук, локальный запуск в режиме polling не получает сообщений — нужен отдельный тестовый бот.
- **Поддержка без нейросети**: отвечает на типовые вопросы по ключевым словам; на остальное честно говорит, что не знает, и предлагает подать заявку.
- **Общего чата дома нет**: API MAX не позволяет боту создавать групповые чаты и добавлять в них участников (метод добавления удаляется из API 30.09.2026).
- Праздничные дни при расчёте сроков в рабочих днях не учитываются (только суббота и воскресенье).

## 15. Порядок остановки и повторного запуска

```bash
docker compose stop                 # остановить, контейнер остаётся
docker compose start                # запустить снова
docker compose restart              # перезапустить (проверка «данные переживают рестарт»)

docker compose down                 # остановить и удалить контейнер; данные в томе app-data сохраняются
docker compose up --build           # повторный запуск (после изменения кода — с пересборкой)

docker compose down -v              # полный сброс: удалить и том с базой и фото
docker compose logs -f app          # журнал
```

При каждом старте контейнер сам применяет новые миграции и перезагружает справочник; привязки и заявки жильцов сохраняются. Остановка штатная: по `SIGTERM` сервис перестаёт принимать события, дожидается обработки начатых и закрывает базу.

На стенде Amvera: «Перезапустить» — перезапуск текущей сборки; после загрузки новых файлов — «Пересобрать» (новая сборка из Dockerfile). Данные в постоянном хранилище `/data` сохраняются в обоих случаях.

## A. Запуск без Docker

Нужны Node.js 20.6+ и npm. Режим `MAX_MODE=polling`: бот сам забирает сообщения, домен и HTTPS не нужны.

```bash
cp .env.example .env          # в корне; вписать MAX_BOT_TOKEN
cd backend
npm install
npm run db:generate           # Prisma Client
npm run db:deploy             # миграции
npm run db:seed               # справочник домов

```

Мини-приложение для разработки: `cd webapp && npm install && npm run dev` (запросы `/api` проксируются на `localhost:3000`). В VS Code то же самое — задачами «1. Подготовить проект» и «2. Запустить бота» (Terminal → Run Task).

## B. Деплой на Amvera

`Dockerfile` и `amvera.yml` в корне собирают один контейнер; постоянное хранилище монтируется в `/data`, порт контейнера — 3000. В переменных задать `MAX_BOT_TOKEN`, `MAX_WEBHOOK_SECRET`, `PUBLIC_BASE_URL=https://<домен>`, `MAX_AUTO_SUBSCRIBE=true` — бот сам оформит подписку на `<домен>/webhook`. Загрузка файлов через веб-интерфейс Amvera не удаляет файлы, которых больше нет в проекте, и не обновляет скрытые (`.dockerignore`); после загрузки — «Пересобрать».

Подписка вручную: `npm run subscribe` (проверит `/health` и токен, создаст подписку и сверит её), `npm run subscriptions` — список, `npm run unsubscribe` — удалить. Не удаляйте подписку рабочего бота — он перестанет отвечать.

## C. API мини-приложения

Все запросы, кроме входа, — с `Authorization: Bearer <token>`. Пользователь берётся только из токена.

| Запрос | Что делает |
|---|---|
| `POST /api/auth/session` `{web_app_data}` | проверяет подпись `initData` MAX, выдаёт `{token, expires_in}` на 1 час |
| `POST /api/auth/link` `{code}` | вход по ссылке из бота (запасной путь) |
| `GET /api/me` | квартира, дом, УК (телефоны — только проверенные), средняя оценка УК |
| `PUT /api/me/apartment` `{house_id, number, entrance?}` | привязать или сменить квартиру; `400 bad_house / bad_number / bad_entrance` |
| `GET /api/houses/search?q=` | поиск дома в справочнике |
| `GET /api/catalog` | категории со сроками и основаниями, лимиты |
| `POST /api/requests/suggest` `{description}` | категория по описанию и признак «газ» |
| `POST /api/requests` `{description, category}` | подать заявку; без квартиры `409`, газ `422`, дубль — `200` с той же заявкой |
| `GET /api/requests`, `GET /api/requests/:id` | свои заявки; чужая — `404` |
| `POST /api/requests/:id/photos` (тело — картинка) | добавить фото к своей открытой заявке, до 5 |
| `GET /api/requests/:id/photos/:photoId` | фото своей заявки |
| `POST /api/requests/:id/resolve` | «Проблема решена» |
| `POST /api/requests/:id/cancel` | отозвать открытую заявку; закрытая — `409` |
| `POST /api/requests/:id/rating` `{value 1–5, comment?}` | оценка выполненной заявки, один раз |
| `GET /api/requests/:id/complaint` | текст жалобы в ГЖИ |
| `GET /api/notifications` | статусы своих заявок и «Соседи уже сообщили» |
| `GET /api/support/start`, `POST /api/support` `{text}` | поддержка: приветствие и ответ `{topic, text, actions, suggestions}` |

Служебные: `GET /health` — живость и доступность базы, `GET /bot` — имя и ссылка бота (без токена), `POST /webhook` — события MAX.

## D. Вебхук: поведение

| Ситуация | Ответ |
|---|---|
| Нет или неверный `X-Max-Bot-Api-Secret` | `401`, тело не разбирается |
| Верный секрет | `200 {"ok":true}` сразу, обработка после ответа |
| Битый JSON | `200` + предупреждение в логе (MAX не должен ретраить) |
| Повторная доставка | `200`, обработчик не вызывается повторно |
| Ненужный тип события | `200`, молча игнорируется |
| Форма события не совпала со схемой | `200`, в логе пути полей без значений |
| Больше 100 событий в минуту от одного пользователя | `200`, событие отбрасывается с предупреждением |

Ключи идемпотентности: `msg:<mid>`, `cb:<callback_id>`, `start:<user_id>:<timestamp>`.
